# 보안 점검

목표: 실제로 악용할 수 있는 약점을 찾는다. 이론상 가능성·모범 사례 목록은 내지 않는다.

## 대상
- 요청에 파일·범위가 있으면 그것. 없으면 `git diff HEAD`(비었으면 `git diff HEAD~1`).
- 셸은 읽기만 (`git diff`, `git log`, 의존성 목록 보기). 파일을 고치지 않고, 밖으로 요청을 보내지 않는다.

## 순서
1. 신뢰 경계를 찾는다: 사용자·네트워크·파일·환경 변수에서 들어오는 값이 어디로 흘러가는지.
2. 위험한 곳까지 값을 따라간다:
   - 주입: SQL·셸 명령·경로·템플릿·로그 줄·HTML(XSS)에 그대로 들어가는지.
   - 인증·권한: 확인을 빠뜨린 경로, 다른 사용자의 ID로 접근(IDOR), 역할 확인 순서.
   - 비밀값: 코드·로그·오류 글·응답에 키·토큰·비밀번호가 보이는지, 비교가 상수 시간인지.
   - 입력 검증: 크기·개수 제한(압축 폭탄·큰 업로드), 형식, 정수 넘침.
   - 경로: `..`·심볼릭 링크로 허용 폴더를 벗어나는지.
   - SSRF: 사용자가 준 주소로 서버가 요청하는지, 내부 주소·리다이렉트·DNS 다시 묶기를 막는지.
   - 역직렬화·파서: 신뢰하지 않는 데이터를 타입 정보와 함께 풀거나 외부 엔티티(XXE)를 여는지.
   - 웹: CSRF, 쿠키 속성(HttpOnly·Secure·SameSite), CORS, 보안 헤더.
3. 각 후보를 공격 시나리오로 확인한다. 이미 막는 코드가 있으면 지운다.

## 답 형식
심각도(높음·중간·낮음) 순:
- `파일:줄` — 약점 한 문장
- 공격: 누가 어떤 입력으로 무엇을 얻는지
- 고칠 방법: 가장 작은 수정

없으면 "찾은 약점 없음"과 본 범위만. 실제 공격 코드를 만들지 않는다.
